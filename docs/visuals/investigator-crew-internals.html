One request, message by message

Joule discovers the agent through its card, sends a single JSON-RPC call, and waits. Inside, the crew calls three different AI services in a fixed order. Dashed arrows are responses.

The four contracts

Each boundary is a small, declarative piece of config or data. These are taken from my project files; the A2A message shows the standard request shape.

Joule → agentinvestigate_function.yaml
action_groups:
  - actions:
      - type: agent-request
        system_alias: INVESTIGATOR_AGENT
        agent_type: remote
        result_variable: "apiResponse"
      - type: message
        message:
          content: "<? apiResponse.body.artifacts[0].parts[0].text ?>"

Design decisions

The choices that shaped the system and why each one holds.

  • Sequential, not hierarchical

    The detective needs both reports before it can reason. A fixed order follows that data dependency and keeps runs reproducible.

    Process.sequential · context=[appraise, analyze]
  • Numbers from RPT-1, facts from documents

    The LLMs only reason over tool output. Every prompt forbids invented values, alibis or evidence.

    "Do NOT fabricate" in agents.yaml
  • A model per role

    The two tool-calling agents run on a fast, cheap model. The one agent that has to weigh evidence gets GPT-4o.

    sap/gemini-2.5-flash-lite · sap/gpt-4o
  • A2A as the only interface

    Joule knows the agent card and nothing else. The crew could be rewritten in LangGraph without touching Joule.

    /.well-known/agent-card.json
  • Config outside the code

    The URL lives in a BTP Destination and the credentials come from a service binding. .env never leaves the laptop.

    Destination · generative-ai-hub binding · .cfignore
  • One worker, in-memory tasks

    A crew run is memory-heavy, so one worker in 1 GB keeps it predictable. Scaling out would need a persistent task store.

    uvicorn --workers 1 · InMemoryTaskStore
